# NEXORA mobile connection contract and outstanding work

This Expo client is separate from the existing web cookie API. Set `EXPO_PUBLIC_NEXORA_API_URL` at build/start time to a **public HTTPS origin only**, e.g. `https://api.example.com` (illustrative, not an active service). No path, query, fragment, credentials, HTTP, localhost or private-address literal is accepted. DNS reachability/public routing still requires operator verification. The origin is public configuration, not a secret. Requests use `credentials: omit`; no web cookies, database credentials, provider keys or web payment routes are used.

No deployed `/api/mobile/v1` service was verified by this audit. A configured origin alone does not make these features operational. 404, 405 and 501 are reported as unavailable. A 2xx mutation with malformed or missing data, a timeout, or a lost response means **save status is unknown**, not that nothing was saved. Refresh and inspect before resubmitting. A complete workspace alone does not prove which concurrent request created an item.

## Proposed wire contract

Successful JSON responses have a `data` envelope. Errors may be `{error:{code,message}}` or `{error:string,code}`. `POST /auth/login` accepts `{email,password}` and returns `{data:{user:{id,email,locale?},accessToken,refreshToken,accessExpiresAt}}`; `POST /auth/refresh` accepts `{refreshToken}` and returns the same shape. `POST /auth/logout` and `/auth/logout-all` send a bearer access token and `{refreshToken}` and expect a JSON `data` response. `/auth/logout-all` means **the current mobile token family only**, not all web sessions or necessarily other mobile families. Server semantics require separate validation.

Authentication POSTs request `redirect: 'error'` and reject observed redirects. A transport rejection is shown as a connection/redirect error. The JS-level `response.redirected` check is only detection after a redirect and does not prevent credential disclosure if a native transport follows it. **Before release, verify on actual iOS and Android builds that their fetch implementation honors redirect refusal for 301, 302, 303, 307 and 308, including cross-origin redirects. If it does not, use a native transport that refuses redirects before sending credentials.** No such native testing is claimed here.

Authenticated calls use `Authorization: Bearer <accessToken>`: `GET /workspace` returns `{data:{workspace}}`. Proposed mutations: `POST /first-check`, `POST /goals`, `PATCH /goals/:id`, `POST /generate`, `PATCH /assets/:id`, `POST /assets/:id/approve` with `{version}`, and `POST /results`. They return a complete updated workspace. Creation requests (`/first-check`, `/goals`, `/generate`, `/results`) additionally send `clientRequestId`; they require a server-authenticated response of the form `{data:{workspace,receipt:{requestId,entityIds:[...]}}}`, with the same request ID and the created entity ID(s) present in the appropriate workspace collection. Field checks are also applied. The server must bind receipts to the operation, authenticated owner and idempotency semantics; echoing input without doing so is not proof. This receipt is a **proposed extension and has not been implemented or verified on a server**. Without it these screens show unconfirmed, even if another item happens to match. Request IDs are correlation identifiers, not authorization credentials; generation retains its idempotency key only during the current screen session. Other creates are not guaranteed idempotent. Receipt support, collision-safe identifiers and durable server-side idempotency require agreement and real integration testing.

Workspace shape contains `profile`, `assessments`, `weeklyPlans`, `assets`, `results`, `executions`, and `generationAvailable`. Server-side ownership, idempotency, entitlement, validation, token rotation/reuse detection, rate limiting and authorization are mandatory; the app cannot replace those checks. The web first-check parser previously inspected does not persist mobile `customerType` and `monthlyGoal`; support must be agreed before those fields are relied on.

## Session, race and cleanup behavior

Access and refresh tokens are stored in Expo SecureStore on native (device-only, unlocked); on web they are process-memory only, so reload signs out. Requests after 401 share one refresh then retry once. Startup refreshes a stored token before accepting a session. Refresh/restore/second-401 failures fail closed and clear local session rather than preserving a possibly rotated or invalid token. There is no guarantee that this locally revoked or lost session was revoked remotely; a service operator may need to revoke the mobile family.

Logout invalidates the local session immediately, waits for an in-flight refresh to return the newly rotated credentials, then attempts remote revocation with those credentials. If the refresh or revoke times out, loses its response, redirects, or otherwise cannot be confirmed, the app reports remote revocation **unconfirmed**. It never retries a rotating refresh blindly. Secure deletion and remote revocation are separate and failures are visible. A deletion failure raises a global warning, including for forced logout and restore, and offers retry; if possible the client overwrites the stored credential with a signed-out marker, which blocks restore and preserves the warning after restart. If **both delete and overwrite fail**, no durable client-side tombstone can be guaranteed: old credentials may remain and may be restored after restart. The warning explicitly says so, blocks new login in the current process and advises service-operator revocation. Clear the device's secure storage and verify remote revocation; do not assume cleanup. The app cannot prove behavior after process termination during a failed storage operation. Real device SecureStore/Keychain lock, migration, deletion, overwrite, reboot and reinstall behavior must be tested.

On user identity change the previous workspace is cleared immediately. Workspace GETs and writes are serialized per identity; late responses from a prior identity are discarded, and a new identity does not wait on the old one. This only orders this app instance's operations, not concurrent changes from other devices or server transactions; server versioning and idempotency remain necessary.

The legacy `/oauth/callback` route is deliberately inert: it neither reads URL tokens nor creates a session. NEXORA email login remains separate. No token or password is intentionally logged.

## Remaining scope / release gates

Five browseable tabs, email login, a business-check form, workspace read, weekly goal create/complete, one text draft request, draft revision/approval and count result entry are wired to the **proposed** API. Nothing is seeded or locally presented as saved. Generation is disabled unless the server explicitly reports `generationAvailable` and supplies a marketing recommendation. Purchases and assumed free allowances are not implemented. Registration, password reset, recording usage, currency/ad-spend results, editing/deleting plans, downloading/copying assets, notifications/opt-out, customer support, policy links, account deletion and data export are not implemented.

Release still requires a real backend and receipt contract, token-family/revocation and rotating-token tests against it, TLS/CORS and redirect verification, secure-storage failure/restart testing on physical iOS and Android, actual-device UI/accessibility checks, and server authorization/idempotency tests. Current automated tests use fakes; they do not establish native network or storage guarantees.
