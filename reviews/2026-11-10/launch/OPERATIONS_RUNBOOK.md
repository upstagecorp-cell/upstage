# 유료 출시 운영 절차

기준: 2026-11-10. 실제 운영 계정 연결 전 사용할 절차이며 실행 완료 기록이 아니다. 총괄 판단과 가격·세금 계산은 [7일 출시 계획](../../../SEVEN_DAY_LAUNCH_PLAN.md)을 따른다.

## 판매자와 외부 서비스

1. 실제 판매 사업체와 계좌, 대표 세금 거주국·근무 장소를 정한다. 미국 LLC와 C-corp 과세를 같다고 가정하지 않는다. 이름·주소·지원 이메일을 약관과 Stripe에 일치시킨다. 한미 소득·급여·배당·간접세·신고를 전문가와 검토한다.
2. 미국 법인을 사용한다면 Stripe의 적격 판매자 심사와 입금 계좌 연결을 마친다. 키를 채팅·저장소·스크린샷에 넣지 말고 호스팅의 비밀 환경변수에 보관한다.
3. Stripe에 Focus $149와 Growth $299 상품을 만든다. 둘 다 USD·정액 월 결제·수량 1·세금 별도(`exclusive`)로 만든다. 연간/체험/쿠폰/추가 좌석은 활성화하지 않는다. 실제 SaaS 제품 분류·사업 주소·필요 등록을 Tax에 설정하고 신고·납부 담당을 정한다. `automatic_tax`만으로 등록과 신고가 끝나지 않는다.
4. 전용 고객 포털 configuration을 만든다. 결제 수단 변경·청구서·기간 말 해지를 켠다. 플랜 변경·수량 변경·구독 일시정지는 끈다. `STRIPE_PORTAL_CONFIGURATION`을 설정한다. 정책 URL·브랜드·고객 명세서 표시·지원 연락처를 실제 판매자 것으로 설정한다.
5. `/api/billing/webhook`에 subscription create/update/delete, invoice paid/payment_failed/payment_action_required, checkout session completed 이벤트를 보낸다. 정상 상태 전체를 조회하므로 이벤트 순서나 checkout 성공 페이지를 권한의 근거로 사용하지 않는다. SDK와 호환되는 현재 API 이벤트를 테스트한 뒤 웹훅 서명 비밀값을 설정한다. 배포 후 웹훅 HTTP 실패와 Stripe 재전송을 관찰한다.
6. Resend에서 소유한 발신 도메인을 인증하고 SPF/DKIM 등 발신 설정을 검증한다. `RESEND_API_KEY`, `NEXORA_EMAIL_FROM`을 설정한다. 인증/복구 메일의 원본 토큰은 로그에 남기지 않는다. 이메일 클릭 추적은 계정 링크에서 사용하지 않는다.
7. `OPENAI_API_KEY`·`OPENAI_MODEL`에 실제 접근 가능한 텍스트 모델을 연결한다. 별도의 프로젝트 예산·알림·속도 제한을 설정한다. 실패나 타임아웃이 공급자 요금을 발생시킬 수 있으므로 사용자 포함량과 공급자 비용 장부를 분리한다.

## 배포 환경과 자료

- Node.js 24.14 이상, 단일 애플리케이션 인스턴스와 영구 볼륨의 SQLite를 사용한다. 임시·서버리스 인스턴스 로컬 디스크나 복수 인스턴스 분산 SQLite를 이 구현에 바로 사용하지 않는다.
- `APP_ORIGIN`은 공개 HTTPS 루트 주소, `NEXT_PUBLIC_SITE_URL`은 같은 값, `NEXORA_DB_PATH`는 보호된 영구 경로다. 프록시와 HTTPS, Secure 세션 쿠키를 운영 브라우저에서 확인한다.
- secrets는 서버에만 둔다. DB·백업·계정 접근 권한을 최소화하고 암호화된 볼륨/백업을 호스팅에서 구성한다. 백업 위치·보관기간·복원 책임자를 기록한다.
- 정기 백업은 SQLite 일관성을 보존하는 방식으로 수행한다. WAL 사용 중인 파일 하나만 임의 복사하지 않는다. SQLite 백업 기능 또는 애플리케이션을 멈춘 일관된 복사본으로 별도 경로에 복원해 레코드 수와 로그인·최근 승인 버전을 검증한다. 원본 운영 DB에 시험 복원을 하지 않는다.
- 오류·가동률·생성 실패/원가·웹훅 실패·메일 실패를 관찰하고 알림 수신자를 정한다. 앱의 사용자 오류 응답은 세부 비밀값을 숨긴다. 별도 APM·호스팅 로그 경보는 아직 운영 계정에 연결되지 않았다.
- `/terms`·`/privacy`는 내용과 실제 위탁자·처리 국가·보관·삭제 절차를 검토한다. 판매자 이름·주소·지원 이메일 및 최종 법적 검토 전에는 초안 표시가 남는다. 제공된 초안을 법률 자문으로 보지 않는다.

## 실제로 통과해야 하는 항목

운영 키를 넣기 전에 Stripe 테스트 모드로 다음을 확인한다. SDK fixture 테스트는 별도 증거이며 이 절차를 대신하지 않는다.

## 구독 운영에서 지켜야 할 구분

- 고객 포함량: 성공 및 현재 실행 중인 패키지 기준. 공급자 비용: 실패/중단/잘못된 응답을 포함할 수 있다. 실패가 많으면 시간당 제한, 기간당 시도 3배 보호, 전체 일일 시도 보호가 먼저 작동할 수 있다.
- 하루 시도 보호 기본값은 서비스 전체 UTC 500회다. 정상 고객 수가 늘면 실제 비용 예산을 확인하고 `NEXORA_DAILY_GENERATION_LIMIT`을 조정한다. 포함량을 축소하는 수단으로 사용하지 않는다. 보호 제한 오류는 지원에서 원인을 확인한다.
- 가격·월 포함량은 `src/lib/billing/plans.ts`의 단일 정의를 화면과 서버에서 쓴다. 기존 구독 가격을 바꿀 때는 이 파일만 편집하지 말고 판매 정책·Stripe price·기존 권리·통지를 함께 검토한다.
- 운영자가 Stripe에서 플랜을 변경한 경우 가격/수량/기간·청구서 상태·포털 설정을 확인하고 동기화한다. 코드의 일치 검사는 알 수 없는 가격이나 수량에 유료 권한을 임의 부여하지 않는다.
- 지원 요청은 인증된 계정과 Stripe 고객을 먼저 대조한다. 계정 비밀번호를 이메일로 받거나 직접 DB 값만 바꾸어 유료 권한을 주지 않는다.

## 공개 전 마지막 설정

1. 기록으로 위 항목의 통과와 정책 검토를 확인한 뒤 `NEXORA_LEGAL_APPROVED=true`, `NEXORA_LIVE_TESTS_APPROVED=true`를 운영자가 설정한다. 이 값은 자동 검증 결과가 아닌 운영자 확인값이다.
2. 실제 운영 Stripe 키와 월 가격 ID, 포털 configuration, 운영 웹훅 키를 사용한다. 테스트와 운영 데이터를 섞지 않는다.
3. `npm.cmd run launch:preflight`로 값의 존재·공개 주소·영구 DB 경로·운영 모드 확인. 키 값을 출력하지 않는다.
4. 외부 서비스 검증이 끝나면 `NEXORA_PAID_LAUNCH_ENABLED=true`로 신규 결제를 연다. 먼저 5~10명 규모로 운영한다.
5. 매일 첫 체크 완료·실제 초안 승인·첫 사용·생성 실패·토큰 비용·지원 시간·환불 요청을 확인한다. 같은 고객의 다음 주 작업을 관찰한다. 다음 달 유료 갱신은 실제 청구서로 확인한다.

문제가 있으면 `NEXORA_PAID_LAUNCH_ENABLED=false`로 **신규 구매만** 닫을 수 있다. 기존 정상 유료 고객 권한과 기존 기록은 이 스위치로 지우지 않는다. 생성 공급자 장애나 데이터 사고는 별도 원인에 따라 대응하고 고객에게 약속한 지원·환불 정책을 적용한다.

## 7일 내 관찰할 고객 지표

첫 체크→명시적 저장→마케팅 작업 준비→첫 유료 구매→첫 승인→실제 사용→다음 주 재사용을 별도로 본다. 샘플 체험 클릭은 실제 생성이나 업무 완료로 세지 않는다. 가격 페이지 방문 이탈을 측정하는 방문 분석 SDK는 이번에 연결하지 않았다. 기존 계정·작업·승인 기록과 Stripe 청구서에서 초기 활성화·원가·구매를 집계할 수 있지만, 결제 실패/고객 취소/환불을 서로 다른 이유로 기록해야 한다.

해지 설문·A/B 테스트·월별 코호트 보드·자동 지원 대시보드는 남은 작업이다. 최초 소수 고객은 수동 관찰과 익명 집계로 시작할 수 있다. 검증 없이 임의의 이탈률 개선 수치를 표시하지 않는다.
